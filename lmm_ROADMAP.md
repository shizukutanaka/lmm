# lmm ROADMAP — Socratic feature derivation

> Generated by 17 rounds of Socratic inquiry (R1-R81), deriving 70 candidate
> features (A-BR) from unexamined assumptions in lmm's premise space.
> Philosophy throughout: **measure, don't trust** — every feature is a hole
> in lmm's current ability to *prove* what it manages.

## Aporia (R81) — the natural endpoint

lmm is a **proxy/hub**. But the runtimes it integrates (Ollama `ollama run`,
LM Studio) already expose single-command UIs. So lmm's unique value is NOT
feature addition — it is **concentrated proof**: proving that the managed
runtimes actually work, and protecting what must be protected.

Therefore the 70 candidates split:
- **~8 are lmm-native** (the proof/guard layer — its real mission).
- **~62 are Ollama/LM Studio re-implementation** (long-tail; only build on demand).

## v1 CORE (build now — lmm's mission)

| ID | Feature | Why it is core |
|----|---------|----------------|
| E  | `lmm doctor` — lmm proves itself | The spine: lmm measures its own backends live |
| M  | backend authenticity probe | Tests claimed capability (e.g. "gpt-4") with benchmark questions |
| Z  | cross-backend diff test | Same prompt → multiple backends, scores agreement (divergence = breakage) |
| AR | chaos harness | Injects backend stop/latency, proves lmm degrades/recovers |
| AX | self-injection defense | Sanitizes control strings; data/command boundary separation |
| R  | secret separation | Refuses plaintext keys in config; env/keychain only |
| V  | privacy mode (`--local-only`) | Hard-disables cloud routes; asserts zero egress |
| A  | backend watchdog | Detects dead backends, auto-restarts Ollama |
| AN | config schema validation | Validates config at startup, rejects with line numbers |

## v2 (practical, after core)

Routing family (B cost / C recommend / X context / BG lighten), G response-health,

## Deferred / excluded (scope = LLMOps platform, not lmm)

BH edge, BM config-lock, BJ api-version, AU power/thermal, AJ i18n, AS
explainable, T library, AA session, BO carbon, BP webhook, BQ --json, BR
model-eol, BA quota, BB sla, AV plugin-sandbox, AW rollback, AD plugin,

## How to use this file

- Pick from **v1 CORE** to extend lmm. Boss plans, subordinate / L25 implements.
- Every addition must answer: *does it prove or protect what lmm manages?*
  If not, it is long-tail — defer.
- Regenerate only when a genuinely new premise layer appears (vertical
  specialization: medical/finance/compliance) — not by repeating R1-R80.

# Fleet features (boss-mode orchestrator) — R82-R101, F1-F20

Derived by pivoting the Socratic inquiry from lmm's premise space to the
**fleet orchestrator's** unexamined assumptions (after lmm generation hit
feature-factory busy-loop). Same philosophy: **measure, don't trust** — applied
to the boss itself.

## v1 CORE (fleet's mission = prove the delegation)

| ID | Feature | Why core |
|----|---------|----------|
| F1 | independent proof of subordinate execution | Boss re-measures side effects (file/process/API), not trusting self-report |
| F8 | human escalation / approval gate | Pauses high-impact ops for human sign-off |
| F14 | boss's own watchdog | The monitor (boss) is itself monitored; auto-restart |
| F15 | cascade kill / full stop | stop signal propagates to all spawn descendants; no zombies |
| F16 | meta-verification of boss verdicts | A 3rd process re-checks "did it actually work" — verifies the verifier |

## v2 (practical)

F2 fallback quality proof, F3 delegation-graph health, F4 structured VERDICT/webhook,
F6 live orchestration view, F7 campaign cost accounting, F9 campaign experience,
F10 priority-route auto-recovery, F17 priority/scheduling, F18 load balancing/fairness,
F19 explainable delegation (--why), F20 delegation safety-guard.

## Long-tail (build on explicit request)

F5 boss-plan persistence, F11 multi-boss coordination, F12 preemption/timeout,
F13 decision-chain audit, F21+ micro-tail (federation, compliance, multitenant fleet).

## How the two roadmaps relate

- **lmm CORE** = proving the *runtimes*. **fleet CORE** = proving the *delegation*.
- Both answer the same Socratic question: *what do we claim works but haven't measured?*
- A feature belongs in lmm if it proves a runtime; in fleet if it proves a delegation.
- If a candidate proves neither, it is long-tail — defer or split into a separate product.

# Domain-specialized modes — R102-R111, Domain-*

Third Socratic pivot (lmm → fleet → domain). Each domain exposes an
unexamined assumption: *the generic tool ignores domain-grade proof*. Every
domain feature is an existing CORE capability (provenance / tamper-log /
deterministic / human-gate) specialized to a domain's legal or practical bar.

| ID | Domain | What generic lmm lacks | Built on |
|----|--------|------------------------|----------|
| Domain-M | Medical | diagnostic citation + non-retention of patient data | AF + V |
| Domain-F | Finance | regulation-grade immutability (SEC/MiFID evidence) | BD + BI |
| Domain-L | Legal | citation existence verification (no hallucinated cases) | M probe |
| Domain-E | Education | grading rationale vs rubric | AS |
| Domain-A | Accessibility | screen-reader / voice I/O | AJ |
| Domain-S | Security | authorized-scope enforcement for attack steps | F8 + BI |
| Domain-P | Law enforcement | chain-of-custody for evidence | BD + BI |
| Domain-SC | Science | experiment reproducibility + provenance | L |
| Domain-C | Creative | originality / style-consistency check | M probe |
| Domain-O | SRE | incident lifecycle / postmortem / MTTR | AK + BB |

## Principle for domain modes

A domain mode is NOT a new capability — it is an **existing CORE proof, raised
to a domain's bar**. Do not build domain features from scratch; specialize
| M/V/R/BD/BI/F8/L/AS. This keeps lmm zero-dep and single-file.

# Constitutional constraints — R112-R116, Const-*

Fourth Socratic pivot. These are **not features** — they are the boundaries
inside which lmm/fleet is allowed to act. Every other capability assumes these
exist; if you remove them, the system becomes dangerous.

| ID | Constraint | Why it is non-negotiable |
|----|-----------|-------------------------|
| Const-1 | autonomy stop condition | When danger signals pile up (continuous failures, budget overrun, scope creep), the system must halt and wait for human sign-off |
| Const-2 | scope-fitness gate | Before executing any task, decide whether it belongs to lmm/fleet at all; refuse out-of-scope work |
| Const-3 | mis-propagation breaker | A wrong boss decision must not cascade to 10 subordinates; detect and freeze similar delegations after one bad call |
| Const-4 | irreversible-operation super-gate | Destructive / public / irreversible ops (delete/publish/transfer) require the highest gate: human + cooling period |
| Const-5 | external health audit | An independent process periodically re-measures "is this system actually delivering value" and exposes systemic self-deception |

## Principle for constraints
A constraint is **not optional** — it is a safety boundary. If a feature
conflicts with a constraint, the feature is deferred or redesigned.

# Time as a first-class constraint — R117-R121, Time-*

Fifth Socratic pivot. Until now time was treated as a limit (timeout/retry).
These features treat **when, in what order, and how often** as governance
inputs, not afterthoughts.

| ID | Feature | Why it is core |
|----|---------|----------------|
| Time-1 | duplicate-execution suppression | Same/similar requests within a short window are cached or rejected — prevents meaningless load and cost |
| Time-2 | order-dependency detection / DAG execution | Tasks with dependencies are executed in valid order; parallelization cannot violate causality |
| Time-3 | execution windows / maintenance windows | Restricts heavy tasks to low-traffic periods (night / weekend); user/system quiet hours |
| Time-4 | deadline × fitness optimization | Chooses the timing most likely to succeed while still meeting the deadline |
| Time-5 | periodic-task detection / auto-proposal | Learns recurring patterns (e.g. every Monday) and proposes scheduled runs |

---

# Observer epistemology — R122-R126, Observe-*

Sixth Socratic pivot. Until now the "human" was treated as a gate (F8/Const-1).
These features treat **what the observer knows, ignores, and believes** as a
first-class concern. Trust is not binary; it has a boundary.

| ID | Feature | Why it is core |
|----|---------|----------------|
| Observe-1 | think-stream / intermediate reasoning exposure | Boss reasoning (candidates, rejections) is streamed to the human; no more black-box verdicts |
| Observe-2 | why-not / exclusion reasoning | For every backend/candidate rejected, show the reason — closes the "why that one?" gap |
| Observe-3 | attention-bandwidth management | Logs are filtered by severity; dangerous signals bypass suppression, routine noise is held back |
| Observe-4 | observer-tracking / audit-of-audit | Records who viewed lmm output and when — makes the watcher themselves watched |
| Observe-5 | uncertainty-band / known-unknowns | lmm explicitly declares "this region is unverified" — proves its own blind spots instead of hiding them |

# How to extend this roadmap

1. **Pivot** when a current subject hits feature-factory busy-loop.
2. **Aporia** — ask what the tool's *mission* really is, before listing more functions.
3. **Const-1..5** are the highest-priority additions: autonomy without boundaries is not useful — it is dangerous.
4. **Time-1..5** and **Observe-1..5** are the next structural layers after core.
5. Every new entry must answer: *does this prove or protect what we manage, or does it just add convenience?* Convenience is long-tail; proof/protection is CORE.
